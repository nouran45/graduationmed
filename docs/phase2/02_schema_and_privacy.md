# Event schema and privacy

## Fields (`security/event_schema.py::SecurityEvent`)
| Field | Meaning |
|---|---|
| `schema_version` | `"1.0"` |
| `event_id` | `evt_<uuid>`; **unique index** → duplicate delivery is detected |
| `timestamp` | UTC, millisecond precision (MongoDB precision; keeps signatures stable) |
| `seq` | order inside one request: 0 = request record, 1.. = audit events |
| `source` | `middleware` (what happened) / `audit` (what it meant) |
| `event_type`, `event_category` | closed vocabulary (see catalogue) |
| `request_id` | `req_…`, generated by the server; a client `X-Request-ID` is ignored |
| `session_id` | pseudonym `session_…` of the server-side session |
| `actor_id` | pseudonym `actor_…` of the authenticated user (null if anonymous) |
| `actor_role` | `anonymous` / `patient` / `admin` — read from the database, never from the token |
| `staff_role` | `owner` / `pharmacist` / `inventory` when the request was authorised through a pharmacy membership |
| `subject_id` | pseudonym `acct_…` of the **account name** a login/registration event concerns (same value for the same e-mail, so failed logins per target account can be counted) |
| `ip_hash` | pseudonym `ip_…` of the client address (`TRUSTED_PROXY_COUNT` aware) |
| `method`, `endpoint_template`, `service_name`, `route_sensitivity` | route **template** (never the raw URL), service label, initial sensitivity low/medium/high |
| `resource_type`, `target_relation`, `target_ref` | what was touched, the *verified relationship* to it, pseudonym `ref_…` of the touched id |
| `authorization_result` | `allowed` / `denied` / null |
| `rule_id` | AUTH-01 … ADMIN-01 |
| `outcome` | `success` `failure` `denied` `rejected` `blocked` `error` |
| `status_code`, `latency_ms` | HTTP result and duration |
| `details` | small allow-listed dict (below) |
| `sig` | HMAC-SHA256 over the canonical event |

## Pseudonyms
Keyed hashes (HMAC-SHA256 with `SECRET_KEY`, domain-separated per purpose, truncated to 16 hex). Deterministic, so detectors can correlate;
not reversible without the server secret. **Consequence:** rotating `SECRET_KEY` changes every pseudonym from then on (and, unless
`EVENT_SIGNING_KEY` is set, invalidates old signatures). Plan the rotation, or set a separate `EVENT_SIGNING_KEY` and keep it stable.
Mapping an alert back to a session (Phase 6) uses `sessions.session_pseudonym` / `sessions.actor_pseudonym`, stored at login.

## Allowed `details` keys
`reason, operation, limiter, permission, model_route, record_count, row_count, file_kind, size_bucket, decision, staff_role, sessions_revoked, status_class`.
Anything else is dropped. Strings must match `[A-Za-z0-9_.:/- ]{1,64}` and must not contain `@` or look like a JWT, otherwise they become `[redacted]`.
Lists/objects are dropped. Tests `test_no_sensitive_content_in_any_event` and the live check in `phase2_acceptance_demo.py` search the stored events for the
password, token, e-mail, names, user/session/branch/pharmacy/prescription ids, file names, diagnosis text, lab values and drug names.

## Deliberately NOT logged
Passwords · JWTs · e-mail addresses · names · medical values, diagnoses, notes · prescription text/drug names · file names and contents ·
request/response bodies · query strings · raw URLs (unmatched paths are recorded as `<unmatched>`) · raw IP · **User-Agent**.
User-Agent is excluded on purpose: our own scenario generator (Python HTTP clients) would otherwise teach a model the shortcut
"python-requests = attack".

## Two honest notes
* Internal failure reasons (`unknown_account` vs `bad_password`, `other_patient` vs `not_found`) **are** stored, because detectors need them.
  They never reach the HTTP response (the answers stay identical) but they make the event store itself sensitive: it is admin-only and
  lives in its own database.
* `prescription.read.denied` is used for three situations (see catalogue); separate them with `resource_type` and `target_relation`.
